# Правила предметной области

> **Статус: частично реализовано.** Реализованы Типы встреч, Слоты, создание Брони (`POST /api/bookings`) и список предстоящих Броней Владельца (`GET /api/bookings`); отмена Брони, Ссылка на бронь, email-уведомления и постоянное хранилище **не реализованы** (разделы ниже помечены). Термины: [`GLOSSARY.md`](../GLOSSARY.md). Решение про время: [ADR 0001](adr/0001-weekly-schedule-in-owner-local-time.md).

## Роли

- Один Владелец на всю систему, без регистрации и аккаунтов. Мультивладельчество не реализуем.
- Гость записывается без аккаунта, указывая имя и email.
- ID Владельца добавляем в модель только там, где он действительно нужен.

## Тип встречи

- Поля: ID, название, описание (необязательное), длительность в минутах, ID Владельца.
- У Владельца несколько Типов встреч. Гость сначала выбирает Тип встречи, затем Слот.
- Владелец создаёт Тип встречи на публичной странице `/owner` (`POST /api/meeting-types`, без авторизации; ссылки с главной нет). Названия могут повторяться. Новый Тип встречи виден Гостю при следующей загрузке главной.

## Валидация (реализовано)

Все правила и константы — в одном модуле backend (`Validation.kt`). Текст сначала обрезается (trim), затем длина считается в символах Unicode (code points), а не в единицах UTF-16.

- Название: 1–100 символов.
- Описание: необязательно, до 500 символов; пустое после trim считается отсутствующим.
- Длительность: целое число минут, кратное 15, от 15 до 240 (дробное, строка, `null` не принимаются).
- Запрос разбирается строго: неизвестные поля JSON отклоняются.
- Ошибки: `400 VALIDATION_ERROR` со списком `fieldErrors {field, message}` (правила, неизвестные поля, неверные типы); `400 MALFORMED_REQUEST` для некорректного JSON; `500 INTERNAL_ERROR` без деталей.

## Расписание

- Одно повторяющееся недельное Расписание на Владельца, общее для всех Типов встреч. Тип встречи определяет только название, описание и длительность.
- Интервалы задаются по дням недели, в один день их может быть несколько (например, 09:00–12:00 и 14:00–18:00).
- Расписание определяется в часовом поясе Владельца (IANA, например `Asia/Almaty`; `OWNER_TIME_ZONE`).
- Сейчас Расписание задано в коде (`Schedule.workWeek`): понедельник-пятница, 09:00-12:00 и 13:00-18:00, выходные недоступны. Редактирования Расписания нет.
- Исключения на даты, праздники, отпуска и буферы между встречами не реализуем.

## Время

- Конкретные моменты (начало и конец Брони) хранятся в UTC. API передаёт их в ISO 8601 с явным `Z`.
- Недельное Расписание хранится как локальные дни недели и интервалы вместе с часовым поясом Владельца, а не как фиксированные UTC-интервалы (переход на летнее время).
- Гость видит Слоты в часовом поясе своего браузера. Корректный расчёт доступности выполняет backend.

## Слоты и Горизонт записи

- Начало Слота выбирается с шагом 15 минут независимо от длительности Типа встречи.
- Слот предлагается, только если он целиком помещается в Интервал доступности и не пересекается с подтверждёнными Бронями.
- Горизонт записи: 14 календарных дней по календарю Владельца (сегодня и следующие 13), а не скользящее окно 14×24 часа. Начало встречи строго позже текущего момента. Группировка дней на экране Гостя идёт по календарю Гостя, границы Горизонта считаются по Владельцу.
- Сетка по часам Владельца; интервалы полуоткрытые `[start, end)`, касание границ не конфликт. Длительность считается в реальных минутах между UTC-моментами: `endAt = startAt + durationMinutes`.
- Переход на летнее время (ADR 0001): несуществующее локальное время Слота не порождает, для повторяющегося берётся первое вхождение. Расчёт Слотов — чистая функция от `Clock`, Расписания, Типа встречи и существующих Броней.
- Минимального времени до записи нет, кроме запрета на уже наступившее начало.

## Бронь

- Каждая созданная Бронь подтверждена сразу, подтверждение Владельцем не требуется. Поля статуса нет: существуют только подтверждённые Брони.
- Отмена и перенос **не реализованы** (будущие требования, см. раздел ниже).
- Пересекающиеся Брони одного Владельца запрещены независимо от Типа встречи. Проверка пересечений атомарная: два одновременных запроса не должны создать конфликтующие Брони.
- Создание (`POST /api/bookings`): тело `{meetingTypeId, startAt, guestName, guestEmail}`, `endAt` считает только backend; клиентский `endAt`, неизвестные поля и `startAt` не в UTC с `Z` дают `400 VALIDATION_ERROR`. Порядок проверок: `400` -> `404` -> `422` -> `409`.
- `422 INVALID_SLOT`: начало не предложил бы расчёт Слотов для этого Типа встречи (Расписание, сетка, Горизонт, прошлое), даже если бы Броней не было. `409 SLOT_TAKEN`: начало корректно, но пересекается с существующей Бронью любого Типа встречи (интервалы полуоткрытые, касание не конфликт).
- Проверка доступности и вставка выполняются в одной критической секции (`BookingRepository.inCriticalSection`, один замок на процесс); Clock читается внутри неё.
- Список Владельца (`GET /api/bookings`, `listBookings`): Брони всех Типов встреч, у которых `startAt` строго позже «сейчас» (Clock), по возрастанию `startAt`, без пагинации. Уже начавшаяся встреча (даже если ещё идёт) и Бронь ровно с `startAt = now` не попадают в список. На `/owner` блок «Предстоящие встречи» показывает время в часовом поясе Владельца (`Owner.timeZone`), обновляется только кнопкой «Обновить» (фонового опроса нет).
- Имя: 1–100 символов после trim (кодовые точки Unicode). Email: до 254 символов, ровно один `@`, непустые локальная часть и домен, в домене есть точка; регистр сохраняется. Один email может иметь несколько Броней, лимитов и подтверждения email нет.
- **Известное ограничение:** ключей идемпотентности нет. Если успешный ответ `201` потерян (обрыв сети), клиент не может это обнаружить, а повторная попытка вернёт `409 SLOT_TAKEN`. Frontend лишь блокирует кнопку «Записаться» на время запроса.

## Ссылка на бронь (не реализовано)

Будущее требование: в API и интерфейсе этого нет, отмены Брони тоже нет. Предполагаемые правила:

- Отмена переводит Бронь в отменённую; отменённая Бронь не блокирует время. Перенос не поддерживается: нужно отменить старую Бронь и создать новую.
- У Брони есть публичный токен, отдельный от внутреннего ID. Токен криптографически случайный, не менее 128 бит.
- По токену без авторизации доступны просмотр и отмена собственной Брони. Срок действия не ограничиваем. После отмены ссылка продолжает работать.
- Отмена выполняется отдельным `POST`-запросом, не `GET`, чтобы случайное открытие ссылки не отменило встречу.
- Токены не записываются в логи приложения.

## Уведомления и хранение

- Email-уведомлений нет. После записи подтверждение показывается на том же экране Страницы записи; отдельной страницы Брони по Ссылке на бронь нет (не реализовано).
- Хранилище (реализовано): in-memory за интерфейсами репозиториев (`MeetingTypeRepository`, `BookingRepository`). После перезапуска сервера данные теряются. Постоянное хранилище (PostgreSQL) не реализовано, лишних абстракций не добавляем.
