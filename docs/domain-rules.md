# Правила предметной области (будущие этапы)

> **Статус: будущие требования, в коде пока не реализованы.** Согласованы в интервью `/grill-with-docs`. Сейчас реализована только главная страница и заглушка Страницы записи со статическими данными. Термины: [`GLOSSARY.md`](../GLOSSARY.md). Решение про время: [ADR 0001](adr/0001-weekly-schedule-in-owner-local-time.md).

## Роли

- Один Владелец на всю систему, без регистрации и аккаунтов. Мультивладельчество не реализуем.
- Гость записывается без аккаунта, указывая имя и email.
- ID Владельца добавляем в модель только там, где он действительно нужен.

## Тип встречи

- Поля: ID, название, описание (необязательное), длительность в минутах, ID Владельца.
- У Владельца несколько Типов встреч. Гость сначала выбирает Тип встречи, затем Слот.

## Расписание

- Одно повторяющееся недельное Расписание на Владельца, общее для всех Типов встреч. Тип встречи определяет только название, описание и длительность.
- Интервалы задаются по дням недели, в один день их может быть несколько (например, 09:00–12:00 и 14:00–18:00).
- Расписание определяется в часовом поясе Владельца (IANA, например `Asia/Almaty`).
- Исключения на даты, праздники, отпуска и буферы между встречами не реализуем.

## Время

- Конкретные моменты (начало и конец Брони) хранятся в UTC. API передаёт их в ISO 8601 с явным `Z`.
- Недельное Расписание хранится как локальные дни недели и интервалы вместе с часовым поясом Владельца, а не как фиксированные UTC-интервалы (переход на летнее время).
- Гость видит Слоты в часовом поясе своего браузера. Корректный расчёт доступности выполняет backend.

## Слоты и Горизонт записи

- Начало Слота выбирается с шагом 15 минут независимо от длительности Типа встречи.
- Слот предлагается, только если он целиком помещается в Интервал доступности и не пересекается с подтверждёнными Бронями.
- Горизонт записи: скользящее окно 14×24 часа от текущего момента. Начало встречи строго позже текущего момента, окончание не позднее конца окна.
- Минимального времени до записи нет, кроме запрета на уже наступившее начало.

## Бронь

- Новая Бронь сразу получает статус `confirmed`, подтверждение Владельцем не требуется.
- Отмена переводит Бронь в `cancelled`. Отменённая Бронь не блокирует время.
- Перенос не поддерживается: нужно отменить старую Бронь и создать новую.
- Пересекающиеся Брони одного Владельца запрещены независимо от Типа встречи. Проверка пересечений атомарная: два одновременных запроса не должны создать конфликтующие Брони.

## Ссылка на бронь

- У Брони есть публичный токен, отдельный от внутреннего ID. Токен криптографически случайный, не менее 128 бит.
- По токену без авторизации доступны просмотр и отмена собственной Брони. Срок действия не ограничиваем. После отмены ссылка продолжает работать.
- Отмена выполняется отдельным `POST`-запросом, не `GET`, чтобы случайное открытие ссылки не отменило встречу.
- Токены не записываются в логи приложения.

## Уведомления и хранение

- Email-уведомлений нет. После записи показывается страница подтверждения, у Брони есть отдельная страница по Ссылке на бронь.
- Хранилище: in-memory за интерфейсом хранения данных. После перезапуска сервера данные теряются. PostgreSQL не подключаем, лишних абстракций не добавляем.
